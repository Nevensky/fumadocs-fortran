fumadocs-fortran writes the API reference of a Fortran code as MDX pages, which a Fumadocs site builds like its
hand-written ones. It reads the sources with its own parser, written in plain JavaScript with no dependencies, and the
doc comments the code already has, in FORD, Doxygen or LAPACK style. It shows what high-performance computing (HPC)
codes use: OpenMP and OpenACC directives, MPI and coarrays, the conditions of the C preprocessor (cpp), and calls into
BLAS, LAPACK and ScaLAPACK. A reference shows one build of the code, the cpp branches that its macros select:
[Generate the reference](/docs/guides/generate#choose-the-build) says how to choose it.

<Callout title="Pre-release">
  fumadocs-fortran installs from GitHub, and its pages, options and components can change in any 0.x version. Until a
  release is tagged, this site describes the main branch, and the [Changelog](/docs/changelog) lists what has
  changed.
</Callout>

## What a page holds

Each module, submodule, program and block data unit gets a page, and so do external procedures, grouped by their
Doxygen `\ingroup` or by file. On a page, each type, interface, procedure, variable and enumeration has a section under
its own anchor, with:

- badges for its kind and for the HPC features it uses, dashed when a cpp condition decides whether it exists;
- its signature, highlighted as Fortran;
- its documentation, as Markdown with maths, such as $\|x\|_2 = \sqrt{\sum_i x_i^2}$;
- its arguments, result, components, type parameters or bindings as a table: a row each, with the type, shape, intent
  and attributes, which opens to the documentation in full Markdown, the declaration, the meaning of each attribute and
  the shape in words;
- hover cards on the kind names and derived types in those tables, which link to their definitions, or to the
  standards for mpi_f08's types and omp_lib's kinds, and on the library routines it calls (BLAS, LAPACK, ScaLAPACK,
  MPI, OpenMP, OpenACC and Fortran's intrinsic subroutines), which link to their documentation; every badge, intent,
  attribute, shape and type parameter's `kind` or `len` says what it means on hover;
- graphs: a type's parents and extensions, a procedure's callers and callees, with library routines in their
  library's colour, and, on a unit's page, what it uses and what uses it, with every unit and the HPC libraries it
  uses on the overview;
- its own code, in a block that opens, numbered as in its file, for an entry of up to 400 lines; with `--repo`, the
  block's header links to the lines on GitHub.

The page's table of contents marks each entry with a letter for its kind: `t` a type, `s` a subroutine, `f` a
function and so on. The [Showcase](/docs/showcase) shows all of it, generated from the project's own example.

## What it does not do

- It reads no configuration file. The command line takes flags, and the options without one are in the
  [JavaScript API](/docs/reference/javascript).
- It has two commands, `dump` and `generate`, and no watch mode. `generate` prints its diagnostics and exits 0, so a
  CI job does not stop on one.
- It reads no fypp sources. A folder's `.fypp` files are not found, and a `.fypp` file named on the command line, or a
  found file in fypp syntax, is skipped with a warning: run fypp first, and generate from the Fortran it writes.
- COMMON blocks, NAMELIST groups and ENTRY points are not shown.
- FORD's `[[name]]` links work in doc comments, not in hand-written pages.
- Next.js is the only framework its pages are tested in.
