# Contributing to fumadocs-fortran

How to work on the package (the parser, the generator, the components, the registry and the grammars) and on its
documentation, and how a release is made. The links here are absolute, so that they work both on GitHub and on the
[documentation site](https://nevensky.github.io/fumadocs-fortran/docs/contributing/), which includes this file.

## Report a problem

Open an [issue](https://github.com/Nevensky/fumadocs-fortran/issues). For a problem with the command line or the
pages it writes, give:

- the command you ran, in full, and all it printed;
- the versions that `npx fumadocs-fortran --version` in the site's folder, `node --version` and `npm --version`
  print, and your system;
- the smallest Fortran file that shows the problem, if you can share one, or the file and line a message names;
- for a site that fails to build on a generated page, the page's file and the line of the error, and the Fortran and
  doc comment of the entity it stops on: the page's `Generated by fumadocs-fortran from …` comment names the Fortran
  file it comes from.

For a mistake or a gap in the documentation, use the
[documentation form](https://github.com/Nevensky/fumadocs-fortran/issues/new?template=documentation.yml).

## Work in Docker

The machine needs Docker, not Node.js: the scripts run each command in a `node:24-bookworm` container, as your user,
with the repository mounted. `scripts/dev.sh` runs a command there, or opens a shell when given none:

```bash
scripts/dev.sh npm test
```

`scripts/docs.sh` runs the documentation site, with its `node_modules` in a Docker volume: `dev` serves it at
http://localhost:3000/docs and reloads as you edit, `build` writes the static export into `docs/out`, and `stop` ends
a server started elsewhere.

```bash
scripts/docs.sh dev
```

With Node.js on the machine, the commands run without the scripts (`npm test`, and `npm install` then `npm run dev` in
`docs/`): Node.js 18 or later for the package, and for the site 22.22 or a later 22, or 24.11 or later.
[docs/README.md](https://github.com/Nevensky/fumadocs-fortran/blob/main/docs/README.md) describes the site's own
files.

## Run the tests

The package has no dependencies, and its tools are not saved in `package.json`: CI installs each one with
`npm install --no-save` at the version its job names in
[ci.yml](https://github.com/Nevensky/fumadocs-fortran/blob/main/.github/workflows/ci.yml), and so do you.

- `npm test` runs [test/run.mjs](https://github.com/Nevensky/fumadocs-fortran/blob/main/test/run.mjs). Each run
  gets a scratch folder under `test/out`, kept, with its path printed, when a check fails. CI runs it on Node.js 18,
  20, 22, 24 and 26, with `react`, `react-dom` and `@mdx-js/mdx` installed, so that the rendering and MDX checks run;
  without them those checks are skipped, as are the site's checks without its `node_modules`.
- `npm run test:registry` checks the HPC registry in `registry/`: counts, size, known entries, links, sources and
  notices, with no network. `npm run registry` builds the registry again from its pinned upstream sources, each
  checked against its SHA-256 (`scripts/registry/build.mjs` lists its options).
- `npm run test:shiki` checks the grammars in `shiki/` with Shiki, tm-grammars and `fumadocs-core` installed, at the
  versions of ci.yml's Shiki job. `scripts/build-grammars.mjs` builds them from tm-grammars, and with `--check` fails
  when `shiki/` differs from what it would write.
- The parser gate checks the parser against public codes, which
  [scripts/fetch-corpus.sh](https://github.com/Nevensky/fumadocs-fortran/blob/main/scripts/fetch-corpus.sh) fetches
  at pinned commits into `.corpus/`:

  ```bash
  scripts/fetch-corpus.sh
  ```

  ```bash
  scripts/dev.sh node scripts/gate.mjs
  ```

  The codes are Reference-LAPACK, ScaLAPACK, json-fortran, Quantum ESPRESSO, stdlib, Wannier90 and miniWeather. They
  keep their own licences, Quantum ESPRESSO's and Wannier90's are the GPL, and they are never committed or shipped:
  only counts are recorded, and no line of them goes into a page.
- On demand: `scripts/oracle/ford.sh` runs FORD 7.0.13 in Docker, and `scripts/oracle/compare-ford.mjs` compares
  every dummy argument with FORD's, field by field; the FORD script is GPL-3.0-or-later, like FORD, and is not part of
  the package. `scripts/search/measure.mjs` measures the static search index of a generated reference, by default
  Reference-LAPACK's, with Fumadocs' own index builder; it needs the docs site's `node_modules`, which
  `scripts/docs.sh` keeps in a Docker volume:

  ```bash
  docker run --rm -u "$(id -u):$(id -g)" -e HOME=/tmp -v "$PWD":/work \
    -v fdf-docs-node-modules:/work/docs/node_modules -w /work node:24-bookworm \
    node scripts/search/measure.mjs .corpus/stdlib src -I include --sample 10
  ```
- CI's Package job lints the package with publint, checks the type declarations with `tsc --strict`, and installs the
  packed package in an empty project, which then generates pages.

The documentation has checks of its own, which need no packages. `npm run check` in `docs/` runs them, the site's
`npm run build` runs them first (prebuild), and `npm test` runs them too:

- [check-docs.mjs](https://github.com/Nevensky/fumadocs-fortran/blob/main/docs/scripts/check-docs.mjs)
  checks the pages against the code: Components against `types/react.d.ts` and `style.css`, Doc comments against
  the keywords of the doc-comment engine, What is read on Generate the reference against the reader's sentinels, the
  versions the pages give against `docs/package.json` and ci.yml, and the status sentence against `statusSentence`.
  It also checks the house rules a reader would trip over (titles, descriptions, headings, step ids, shell blocks,
  commands the help lacks) and the sidebar's `meta.json` files.
- [gen-examples.mjs](https://github.com/Nevensky/fumadocs-fortran/blob/main/docs/scripts/gen-examples.mjs)
  `--check` checks the examples of Doc comments against what the package writes for them (see
  [Change the Doc comments examples](#change-the-doc-comments-examples)).
- [check-cli.mjs](https://github.com/Nevensky/fumadocs-fortran/blob/main/docs/scripts/check-cli.mjs)
  checks Command line against the command's help, its messages, the diagnostics `src/` writes and the exit codes. The
  page includes the help from `docs/snippets/cli/help.txt`; after a change to the help, write the file again with
  `--write` and commit it.
- [check-api.mjs](https://github.com/Nevensky/fumadocs-fortran/blob/main/docs/scripts/check-api.mjs)
  checks JavaScript API against the entry points' exports and the types in `types/`.
- [check-readme.mjs](https://github.com/Nevensky/fumadocs-fortran/blob/main/docs/scripts/check-readme.mjs)
  checks the README and this file: their prose; their links, which are absolute, as they are read on GitHub, on npm
  and on the site; the README's install line and status against Get started's; and the map of the code to its pages.

```bash
scripts/dev.sh npm run --prefix docs check
```

CI's Docs job builds the static site under the base path `/fumadocs-fortran`, as GitHub Pages serves it. The build's
postbuild,
[docs/scripts/check-links.mjs](https://github.com/Nevensky/fumadocs-fortran/blob/main/docs/scripts/check-links.mjs),
then checks every link, anchor and page action of the export, and the absolute URLs of its metadata, sitemap and
`llms.txt`. `scripts/docs.sh build` runs the same `npm run build`, so on your machine build the export under the base
path:

```bash
NEXT_PUBLIC_BASE_PATH=/fumadocs-fortran scripts/docs.sh build
```

Before every deploy,
[docs.yml](https://github.com/Nevensky/fumadocs-fortran/blob/main/.github/workflows/docs.yml) runs the commands of
[Get started](https://nevensky.github.io/fumadocs-fortran/docs/get-started/) as a reader would, with
[test-get-started.mjs](https://github.com/Nevensky/fumadocs-fortran/blob/main/docs/scripts/test-get-started.mjs) in
`docs/scripts/`: in an empty folder whose `src/` is a copy of `examples/modern/src`, with the commit it deploys packed
in place of the page's GitHub install line, and then the guides' checks on the site it made. Once a week it runs
with `create-fumadocs-app@latest`, with Node.js 22 and 26, and with the GitHub install itself. A change to Get
started, to a guide it checks, or to what their commands print, has to pass it; the script's first lines list its
options.

## Change the Showcase

The [Showcase](https://nevensky.github.io/fumadocs-fortran/docs/showcase/) is generated from `examples/modern`, which
is MIT like the package:
[docs/scripts/gen-showcase.mjs](https://github.com/Nevensky/fumadocs-fortran/blob/main/docs/scripts/gen-showcase.mjs)
writes `docs/content/docs/showcase/modern/` and `docs/content/docs/showcase/sources.mdx`. After changing the example
or the generator, write them again and commit what changed:

```bash
scripts/dev.sh node docs/scripts/gen-showcase.mjs
```

CI's Docs job runs it too, and fails when the committed pages differ from what it writes. The rest of `showcase/` is
written by hand.

## Change the Doc comments examples

The examples on [Doc comments](https://nevensky.github.io/fumadocs-fortran/docs/reference/doc-comments/) are
generated: each is a Fortran file in `docs/snippets/doc-comments/` and the partial beside it, which
[docs/scripts/gen-examples.mjs](https://github.com/Nevensky/fumadocs-fortran/blob/main/docs/scripts/gen-examples.mjs)
writes through `generate()`. After changing a file there, or what the package writes for one (`src/docs/`,
`src/emit/`, the parser), write them again and commit what changed:

```bash
scripts/dev.sh node docs/scripts/gen-examples.mjs
```

The docs build runs it with `--check` first, and fails when a partial differs from what it writes.

## Edit the documentation

The pages are MDX in `docs/content/docs/`, and each folder's `meta.json` orders the sidebar. They are built with
Fumadocs as `docs/package.json` pins it (`fumadocs-core` 16.19.4, `fumadocs-ui` 16.19.4 as `@fumadocs/base-ui`,
`fumadocs-mdx` 15.6.3, Next.js 16.4.6). A page uses only the components that `docs/components/mdx.tsx` registers.
A step of a tutorial is a heading written `## 1. Create the site [#create-the-site]`: remarkSteps, which
`docs/lib/source.ts` adds, makes it a numbered step, and as it runs after the headings get their ids, a step heading
without its own id would get one with its number in it (`1-create-the-site`).

The house style:

- British spelling: -ise, colour, licence as the noun and license as the verb.
- Fumadocs in prose, and package names in code font (`fumadocs-ui`); fumadocs-fortran, the project's name, as it is.
- Plain, concrete sentences in the present tense; no marketing words, and no time words such as now, currently, new
  or soon.
- No comma before the "and" or "or" that ends a list, unless the list needs one to be read right.
- Headings in sentence case, without code font.
- One shell command per bash block, without a `$` prompt.
- Prose lines of at most 120 characters, front matter included, and a description of at most 107 characters,
  quoted when it holds ': '.
- Each fact on one page, which the others link to. A page links only to pages that exist, with `/docs/…` links
  inside the site; the README and this file link with absolute addresses.
- Examples from `examples/modern`, or written for the page; never code from a GPL project such as Quantum ESPRESSO
  or Wannier90.
- Once a version is tagged, an option or a component added after it carries "(unreleased)" on its page until the
  next release.

[test/site.test.mjs](https://github.com/Nevensky/fumadocs-fortran/blob/main/test/site.test.mjs), part of `npm test`,
runs the documentation's checks and binds these pages and files to the code:

- the Components page: its live examples, the CSS snippets it shows against the site's own files, and its Meanings
  and Styling against `style.css`;
- the Mermaid component of Set up your site, and what Publish on GitHub Pages says of the components' links;
- the Introduction's list of what a page holds, and the home page's sample against the generated entry it copies;
- the 120-character rule on the hand-written pages (the Showcase's own page among them), `README.md`,
  `CHANGELOG.md`, `docs/README.md` and this file.

A change that moves one of these changes the test in the same commit.

## Make a release

A release is a commit on `main` that CI and docs.yml have passed, and a tag on it.

1. In `CHANGELOG.md`, read the section `## 0.1.0 (unreleased)` against the code, and give it the date of the release
   in place of `unreleased`: `## 0.1.0 (YYYY-MM-DD)`. Changes after the release go into a section above it, headed
   `## Unreleased` until the next release names it.
2. Set the version in `package.json` (`"version": "0.1.0"`), and add it and the date to `CITATION.cff`:
   `version: 0.1.0` and `date-released: "YYYY-MM-DD"`.
3. Reword the status sentence for the release: `statusSentence` in `docs/lib/shared.ts`, which the home page and the
   footer show, and its copies in Get started's Pre-release callout, the Introduction and the README. check-docs
   fails when a callout lacks the constant's, and check-readme when the README lacks Get started's or the
   constant's.
4. If the package goes to npm, change the install line to `npm install fumadocs-fortran`, in the README and on Get
   started at once: check-readme fails when they differ, and the Get started test, which replaces the line with the
   packed commit, has to find it. With the GitHub install, the line can name the tag instead
   (`npm install github:Nevensky/fumadocs-fortran#v0.1.0 --allow-git=root`).
5. Generate the Showcase and the examples of Doc comments again (`scripts/dev.sh npm run --prefix docs gen`), and
   commit what changed.
6. Run every check: CI passes on the release commit, and docs.yml passes when run by hand from the Actions tab, once
   as it is and once with "weekly".
7. Tag the commit, and push the tag:

   ```bash
   git tag -a v0.1.0 -m "fumadocs-fortran 0.1.0"
   ```

   ```bash
   git push origin v0.1.0
   ```

8. On GitHub, make a release from the tag, with the CHANGELOG section as its notes. If the package goes to npm,
   `npm publish` runs the tests and the registry checks first (`prepublishOnly`).

## Glossary

- **Badge**: a label beside an entry's heading (`FortranBadge`): its kind, such as subroutine or type, an attribute,
  such as pure or `bind(c)`, an HPC feature (OpenMP, OpenACC, offload, CUDA Fortran, MPI, coarrays) or a cpp
  condition.
- **Pill**: a label inside a table row: an intent, an attribute, a shape or a condition such as `when USE_MPI`.
- **Card**: what a name opens on hover or keyboard focus (`FortranRef`): a kind name or derived type with its
  definition, or a library routine from the registry with its summary and a link to its documentation.
- **Entry**: an entity's part of a page: its `###` heading, signature, badges, documentation, tables, graphs and
  source block.
- **Row**: a line of an entry's table of arguments, results, components, type parameters, bindings or enumerators
  (`FortranArg`), which opens to its documentation and declaration.
- **Source block**: the block under an entry that opens to its lines of Fortran (`FortranSource`), numbered as in
  its file.
- **Registry**: the names of the HPC libraries in `registry/`, which the generator reads for the cards, their links
  and the colours of the graphs.
- **Model**: what the parser builds from the sources, and `dump` prints: every entity under a stable ID, the files
  read, and diagnostics.
